# 学习路线：从插件到命令行工具链（commit-driven）

> 核心方法：**一步一 commit**。每步 = 一个可验证的里程碑，commit message 写清三要素：**改动 / 验证 / 收益**。完成时 `git log --oneline` 就是你的工具链学习目录。

## 目标

把 VS Code + AT32 插件的黑盒工作流，迁移为 **CMake + OpenOCD + GDB 命令行全家桶**：
看得见、可脚本化、可进 Git/CI、换调试器一行搞定、换芯片只改配置。

## 三层架构认知（地基）

| 层 | 管什么 | 本工程对应物 | 迁移状态 |
|---|---|---|---|
| 配置层（图形化） | 芯片怎么用：引脚/时钟/外设 | `*.ATWP`（AT32 Work Bench） | **保留，照常使用** |
| IDE/编辑器层 | 写代码界面 + 点按钮调工具链 | 插件（AT32 扩展）→ 逐步替换 | **被替换中** |
| 工具链层 | 代码→固件→跑起来 | CMake / Ninja / GCC / OpenOCD / GDB | **亲手掌握中** |

关键：配置层与工具链层**解耦**——ATWP 只生成代码，CMake 只管编译，互不干扰。换 IDE/工具链，ATWP 流程零改动。

## 设计决策记录（崩溃记录器：crash.c vs 钩子区）

- **user code 钩子机制**：ATWP 每个生成文件里的 `add user code begin/end` 是**保留区**——重新生成时标记间内容原样保留（和 CubeMX 的 USER CODE 相同）。想在不脱离图形化配置的前提下加代码，写进钩子区。
- **为什么崩溃记录器不写进钩子区**：user code 区在**函数体内**，函数签名/属性（naked）由生成器决定。崩溃现场必须**裸装入口**（异常入口第一条指令抓 SP/R4-R11，此刻寄存器还是故障瞬间值）——普通 C 函数的编译器 prologue 会先压栈污染 SP。
- **落地方式**：crash.c 用**强符号覆盖 startup 的 WEAK handler**（向量表直接指向 naked 入口），代价是与生成代码的 4 个重复函数冲突——**ATWP 重新生成后需手动删除 at32f421_int.c 里恢复的 HardFault/MemManage/BusFault/UsageFault**。
- **权衡**：钩子区方案（零冲突、自动保留）可接受，但 SP 偏差几个字、无 R4-R11，栈回溯精度降级。
