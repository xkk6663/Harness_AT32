# 经验总结：从"点按钮"到"掌控工具链"

## 一、认知升级（三条最重要的认知）

1. **插件 = 壳，按钮 = 命令**。AT32 插件的"编译/烧录/调试"按钮背后，就是 `cmake --preset` + `cmake --build` + `openocd program` + `gdb target remote` 这几条命令。壳的价值是方便，代价是**你不知道、也改不了**。迁移的本质 = 把命令拿回自己手里。

2. **三层解耦**（配置层 / IDE层 / 工具链层）。ATWP（.ioc）只负责生成代码，和 IDE、工具链完全无关。所以：换 IDE、换构建系统、换调试器，**图形化配置流程一行不改**。这也是为什么 CubeMX/ATWP 能同时导出 MDK/IAR/CMake/Eclipse 工程。

3. **开源 = 生态 = 推广（飞轮）**。GCC/CMake/OpenOCD/GDB 免费、跨平台、可脚本化，是全世界嵌入式的事实标准（ST/瑞萨/乐鑫/Pico 全是这套）。学会一套，通吃所有 ARM 芯片；Keil 这类闭源工具链是反飞轮。

## 二、方法层面：commit-driven learning 为什么有效

- **一步一 commit**：diff 是最小可读知识单元，比教程强——被动看 vs 主动读。
- **三要素 commit message**：`改动 / 验证 / 收益`——commit message 就是学习笔记，`git log --oneline` 就是学习目录。
- **每步可验证、可回退**：敢改，因为随时 `git reset`。
- **验证要有预期**：先写"预期输出"再跑，对照即内化（不是跑一下就算）。

## 三、已获得的收益（真金白银）

1. **解决了插件都搞不定的问题**：插件烧录失败（bulk 配置不匹配 DAPLink），自己换 HID 配置秒解决——掌控配置的价值直接兑现。
2. **烧录可脚本化**：`tools\flash.ps1` 一条命令，带前置检查 + 退出码，随时可进 CI。
3. **构建输出全可见**：-Wall 揪出电机库 4 个未使用参数警告；FLASH/RAM 占用率一次构建全透明。
4. **理解了芯片识别链路**：DPIDR 0x2ba01477 = at32f421xx.cfg 期望的 CPUTAPID——从"玄学"到"证据"。
5. **踩坑即学习**：编码、接口后端、TCL 转义、双目录——每个坑都是插件黑盒永远教不了的。

## 四、工具链世界观（下一步的框架）

- **换调试器** = 换 `openocd/interface/*.cfg` 一行（HID/BULK/J-Link/ST-Link）。
- **换芯片** = 换 `target/*.cfg` + 链接脚本 + 启动文件 + toolchain 的 `TARGET_FLAGS`。
- **框架化（elab 哲学）**：把公共逻辑抽成 `cmake/core.cmake` + `boards/*.cmake`（5 个变量描述一颗芯片），工程只写 app 源码 + 选板。ST/AT32 两个 TEST 工程可并入同一框架。
- **CI**：`cmake --build build/Debug` 放 GitHub Actions，push 自动出固件。
- **coredump**：HardFault 现场转储 + GDB `bt` 定位崩溃函数——插件给不了的能力。

## 五、生成器的钩子机制与"精确现场"思维（Step 6 认知）

1. **user code 钩子区**：ATWP/CubeMX 在生成文件里埋 `add user code begin/end`（或 `USER CODE BEGIN/END`）——标记间内容在重新生成时**保留**，标记外被覆盖。安全加代码 = 写进钩子区；加了钩子区外的代码，重新生成会**静默丢失**。
2. **裸装入口（naked）**：崩溃记录器这类"要第一时刻寄存器"的代码，普通 C 函数做不了——编译器 prologue 在函数第一条语句前就压栈了（SP 污染）。必须让向量表直接指向 naked 汇编入口。
3. **强符号覆盖 WEAK**：startup 的 handler 都是 `.weak` 符号，C 文件定义同名强符号即可接管向量表——不用改汇编。代价：与生成代码里的强符号冲突（multiple definition），需删生成代码的重复定义。
4. **设计权衡思维**：零冲突（钩子区）vs 精确现场（naked）不可兼得——先想清楚"精度是否必要"，再选结构。Step 6 选了精确版，因为 SP 差几个字 = 栈回溯错一个函数。

## 六、给未来的自己

- 保持"每步绿"：编译不过的中间态不提交。
- 保持"三要素"：任何一步 commit 都能回答"改了什么 / 怎么验证 / 得了什么"。
- 工具链文档（docs/）随工程走，换电脑一键恢复。

## 七、双层执行架构与数据源思维（Step 7~8 补认知）

1. **嵌入式项目是"中断环 + 主循环环"双层结构**：电机库高速环（TMR1 中断）与初始化/协议（主循环）是两个独立环——编译过 + 一个环在跑 ≠ 全部在跑。找"没跑起来的代码"先问"哪个环负责它、挂上了吗"（踩坑指南第 13 条）。
2. **仪表盘"不更新"先问数据源**：dashboard 串口面板曾冻结，根因不是前端 bug，而是数据源是 `logs/serial.log`（需 serial.ps1 常驻落盘），实测时用内联读串口没落盘 → 面板停更。解决：服务端直接持有串口实时推流（/api/serial 增量轮询），前端 live 追加——**把"落盘中转"换成"服务端持有"**，实时性由数据所有权决定。
3. **头文件内调用顺序也是工程问题**：static inline 函数引用定义在后的同名函数 → 编译报"static follows non-static"（反直觉报错）。头文件也是代码，也有依赖顺序，前向声明是通用解法。

## 八、主循环频率是隐含契约 + 第三方库的"默认调试遥测"是毒药（Step 9~10 补认知）

1. **主循环频率是隐含契约**：电机库状态机按 ~100Hz 主循环设计（靠串口发送天然限速）。任何"让主循环变快"的改动——禁用遥测发送、删延时、优化掉阻塞——都会让 `Func_Start/Stop/Set_Ubus` 等状态机操作从 ~100Hz 飙到几千 Hz，**上电 ~75 秒后状态机被拖死**（心跳 tick 停、中断冻结、但 CFSR/HFSR=0 无硬故障）。修复姿势：**时间节流**（`wk_timebase_get()` 10ms 门槛）+ **状态翻转才动作**（Start/Stop 只在 running 标志翻转时调一次）。教训：**改动前先识别"谁在限速"**——串口发送、延时都是隐含节拍器，拔掉后必须显式补节流。
2. **第三方库的调试遥测默认关**：`Printf_TX_Loop` 把整个 `PRINTF_STRUCT` 原始内存发串口（fdata 未填充 = NUL 洪流 + 拖慢主循环 + 限速副作用）。移植第三方库第一步：**审计它的"每轮都发/每轮都做"的调试代码**，找到就加开关默认关——库作者的调试输出不是给你的，是给他自己的。
3. **串口面板"不刷新"的排查顺序**：① 服务端数据还在流动吗（/api/serial tick 递增）→ ② 面板行里有没有垃圾流淹没（NUL/0x7F）→ ③ 前端轮询/缓存。**先数据源后前端**，90% 的"面板不动"是数据源问题（垃圾流淹没 / 串口独占 / 固件死了），不是 JS bug。
4. **端口独占纪律（升级版）**：串口同一时刻只能一个持有者——`serial.ps1`、`dashboard_server`、`openocd`（调试时挤占透传）三方互斥；排查顺序永远是**先查进程（openocd/serial/dashboard）再开串口**。dashboard 服务是常驻持有者，临时观测用 `serial.ps1` 前先停服务。

## 九、OTA 平台化（M0~M3）：共享核心库 + 状态机回归 + 上位机 profile 化（Step OTA 补认知）

1. **"平台化移植"的正解 = 抽核心 + 留回归基准**：把协议/CRC/Flash 存储/状态机抽成 `ota/core`（纯 C、零芯片依赖），STM32 老工程开 `USE_SHARED_OTA_CORE` 开关指向同一份代码——**双构建哈希一致（bin 8944B / SHA256 相同）即证明抽得干净**。没有回归基准的"重构"都是裸奔。
2. **三个"反直觉"的 Boot 行为（上位机/测试设计前必须背下来）**：① 升级结束判定**不能靠 QUERY_STATE**——Boot 置 SUCCESS 后 `while(1)` 防串口噪声冲写，命令帧一律不响应，只能靠**监听 "Upgrade complete. Final CRC" 打印** + **硬件复位**（openocd `reset run`）；② 固件**最后帧必须截断到实际大小**——上位机按 APP_SIZE 填充 0xFF 打包，Boot 的"最后帧不满 128 自动结束"永不触发 → 状态停留 UPGRADING；③ CRC_FAIL 分支 `while(1)` 等 `'!'` 重触发，也不响应命令帧——重触发靠发 `'!!!!!'` 而不是协议命令。
3. **上位机双 profile 是"一个工具打两家"的最小结构**：config.py 把 Flash 布局（packet_size/app_start/app_size/bootloader_size）+ 触发模式（AT32 bang5 / STM32 single）参数化，core 层全读 config——新增芯片 = 加一个 dict，不动协议/发送代码。
4. **测试工具的自我验证闭环**：`cli_flash.py`（无 GUI）触发 → 轮询 offset → 逐帧发送(ACK/NAK 重传) → 监听升级完成打印 → openocd 硬件复位 → 监听 APP 心跳——CI/AI 可全自动调用，还顺带验证了 NAK 重传（破坏帧 101 的 CRC → Boot NAK → 重传 1 次 → 升级完成 CRC 0x9EE5BE44 与预计算一致）。
5. **状态页注入测试法（M4 方法论）**：Boot 的分支（READY 擦除 / UPGRADING 续传 / CRC_FAIL 等重触发）不好在运行时自然触发，就用 openocd 把状态页（页62 偏移 / 页63 状态）直接 program 成目标状态，再软复位让 Boot 走对应分支——**用注入代替长流程**，把"难复现的分支"变成"可编程的测试用例"。注意：openocd program 路径必须正斜杠（反斜杠被当转义符吞掉）。
6. **硬件环境是回归的一部分，且会反复打脸**：DAPLink CDC 假死（openocd 连续连接后 0 字节，软复位唤不醒、等 5s+重开串口能恢复）、重插后 Flash 非本工程固件（串口出现未知 `[alive]` 打印）——这些"环境坑"会打断自动化回归。**自动化脚本要内置 CDC 恢复期（每个 openocd 调用后 sleep 8s+）和"重开串口"重试路径；回归前先重烧 Boot+APP 锚定固件身份**。
