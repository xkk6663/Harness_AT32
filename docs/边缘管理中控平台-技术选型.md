# 嵌入式边缘管理中控平台 — 技术选型与"一切皆插件"架构设计

> 版本：v0.1 ｜ 日期：2026-10-04
> 范围：把 `dashboard`（AT32 驾驶舱：编译/烧录/调试/串口遥测/看门狗）与 `STM32-OTA-QT` 的 PyQt6 上位机（OTA 升级/固件管理）融合为一个**嵌入式边缘管理中控平台**；讨论技术选型，并评估借鉴 DeepSeek Harness"一切皆插件"的构建方式。本文是选型讨论与架构设计，不含代码实现。

---

## 0. 结论先行

**推荐：Web 平台为主体（Python 后端 + 浏览器前端），OTA 上位机的 Python 核心逻辑并入后端，PyQt6 壳丢弃；插件化采用"轻量 Cordis 式"三档渐进，不做重内核。**

四个核心理由：

1. **驾驶舱已是 Web 架构**（`dashboard_server.ps1` HTTP 服务 + `dashboard.html` 原生前端），四大面板、动作接口（`/api/action`）、串口重连、看门狗已全链路验证——融合的天然地基，不需要推翻重来。
2. **OTA 上位机的价值在核心逻辑不在 UI**：`protocol.py`（帧协议）、`firmware.py`（固件解析）、`iap_worker.py`（重传/续传/进度）、CRC32/状态机全部与芯片无关、零 Qt 依赖——直接搬进 Python 后端就是服务；PyQt6 壳反而是最不值钱、最该丢弃的一层。
3. **边缘管理的场景属性决定了 Web 更合适**：本机 localhost + 局域网 IP 即可远程访问、浏览器零安装、AI 可通过 HTTP API / 事件流接入——这些是"边缘管理中控"的核心诉求，Qt 桌面进程都费劲。
4. **"一切皆插件"与 Web 平台同构**：DeepSeek Harness 的 Cordis 内核只做加载/卸载/依赖管理，模型/工具/会话/UI 全是插件；映射到中控平台就是"内核（插件管理器）+ 能力插件（build/flash/debug/serial/ota）+ 面板插件（前端注册式）"——用 Python 插件注册 + 前端面板注册即可实现同构理念，无需引入 Node/Cordis 那种重运行时。

## 1. 现状能力盘点（融合的输入）

### 1.1 驾驶舱 dashboard（已有，全链路验证）

| 层 | 技术 | 能力 |
|---|---|---|
| 前端 | `dashboard.html`（原生 JS/HTML，无框架） | 四大面板：编译 / 烧录 / 调试 / 串口日志；按钮触发动作；实时开关；最后更新徽标 |
| 后端 | `dashboard_server.ps1`（pwsh 7，HttpListener） | `/api/status` `/api/serial` `/api/log` `/api/action`（build/flash/reset/reconnect_serial 白名单）；串口自动重连（目标端口→自动探测→15s 无数据强制重连）；蓝牙虚拟串口排除 |
| 保活 | `watchdog.ps1` | 30s 探测、服务挂了自动拉起、防多开 |
| 底层动作 | `build.ps1` / `flash.ps1` / openocd / gdb | CMake+Ninja+GCC 构建；OpenOCD 烧录；GDB 调试；日志落盘 `logs/` |

**已具备的"插件化雏形"**：动作接口已是白名单 + 异步执行 + 运行状态跟踪（`running[]`）——这正是插件调度的最小形态。

### 1.2 OTA 上位机 iap_host_tool（待并入，PyQt6）

| 层 | 技术 | 能力 |
|---|---|---|
| UI | PyQt6（桌面） | 固件拖放、实时进度条、TX/RX 包着色监视、百分比限制发送、CRC 破坏模拟、查询/重置/续传 |
| 核心逻辑 | `core/protocol.py` / `firmware.py` / `iap_worker.py` | 帧协议（SOF/EOF + 长度）、CRC32、重传（≤3 次 SEQ）、断电续传、5 状态升级状态机、BIN/HEX 解析 |
| 通信 | pyserial → USART1 115200 | 与固件 Bootloader 的传输通道 |

**核心逻辑零 Qt 依赖**——`protocol.py` / `firmware.py` / `iap_worker.py` 全是纯 Python，搬进 Web 后端无需改动（仅两处常量参数化：`APP_START_ADDRESS`、`APP_SIZE`）。

### 1.3 固件侧（中控平台管理的对象）

- AT32F421G8U7 BLDC 电调固件（Bootloader + APP 双 target，见 OTA 移植方案 §2.2）
- 心跳/遥测串口协议（`[I][tick] heartbeat ... adc[...] pwm[...]`）
- 崩溃记录（crash/coredump）
- 未来：OTA 升级链路（Bootloader 协议）

## 2. 技术选型对比

### 2.1 候选方案

| 维度 | A. Qt 桌面端（PyQt6 合体） | **B. Web 平台（Python 后端 + 浏览器）** | C. Tauri/Electron 桌面壳 |
|---|---|---|---|
| 驾驶舱复用 | 需重写 dashboard 为 Qt 或嵌 WebView | **零迁移，HTML 直接升级** | 复用 HTML，加壳 |
| OTA 核心复用 | 直接并入（同为 PyQt6） | **直接并入（纯 Python 后端模块）** | 需要桥接层 |
| 分发 | pyinstaller 打包 | **浏览器即用，零安装** | 打包安装包 |
| 远程访问 | 桌面进程难 | **localhost + 局域网 IP 天然支持** | 需额外网络服务 |
| AI 可接入 | 需 CLI/HTTP 桥 | **HTTP API + SSE/WebSocket 天然** | 需桥接 |
| 插件化 | Qt 插件机制（重） | **Python 插件注册 + 前端面板注册（轻）** | npm 插件（接近 DSH 生态但引入 Node/Rust） |
| 工具链成本 | Python + Qt | **Python + 现有 pwsh 脚本复用** | Python + Node/Rust（重） |
| 学习成本（嵌入式背景） | 中 | **低（复用现有 dashboard 心智）** | 高 |

### 2.2 为什么放弃 Qt 作为中控平台主体

- **重复劳动**：dashboard 的编译/烧录/串口/看门狗闭环已经 Web 化并验证；用 Qt 重做一遍同等能力，是纯粹的负资产。
- **Qt 的价值只剩 UI 壳**：OTA 上位机值得保留的是 `protocol.py` / `firmware.py` / `iap_worker.py`（纯 Python），PyQt6 的窗口/控件在 Web 下用 HTML 重写 OTA 面板成本更低、更美。
- **"简洁美丽"**：现有 dashboard 深色紧凑风格已是很好的 UI 语言，HTML/CSS 迭代速度远超 Qt 布局，插件面板注册天然适合 Web。
- **边缘管理定位**：Qt 桌面进程做"管理中控"（多设备、远程、可脚本化、可 AI 驱动）反直觉；Web 服务 + 浏览器是标准答案。

### 2.3 为什么不用 Tauri/Electron

- 引入 Node/Rust 工具链，对一个嵌入式工程师是额外负担；
- 分发收益（安装包）不匹配"本机 + 局域网"的边缘场景；
- 插件化若走 npm 生态（DSH 风格），学习成本陡增，且与现有 Python/pwsh 资产割裂。

### 2.4 推荐技术栈（方案 B 细化）

| 层 | 选型 | 说明 |
|---|---|---|
| 后端框架 | **FastAPI（或 aiohttp）** | 异步、SSE/WebSocket 原生支持（串口遥测推送、OTA 进度推送） |
| 串口 | **pyserial** | 复用驾驶舱串口重连状态机逻辑（目标端口→自动探测→15s 无数据重连→蓝牙排除） |
| 底层动作 | **subprocess 调现有 pwsh 脚本** | build.ps1 / flash.ps1 / openocd / gdb 全部保留，后端只做调度与日志——**初期零风险迁移** |
| OTA 核心 | **直接搬入 `ota/protocol.py` `firmware.py` `iap_worker.py`** | 纯 Python 零改动，包成 OTA 服务模块 |
| 前端 | **原生 JS/HTML（延续 dashboard.html）** | 不引框架；面板 = 插件注册的卡片 |
| 前端实时 | **SSE（服务端事件流）** | 心跳/遥测/升级进度推送，比轮询优雅 |
| 保活 | **沿用 watchdog.ps1 + 服务内自愈** | 已有，不动 |
| 配置 | `config.yaml`（或 `plugins.yaml`） | 设备档案（COM/波特率）、目标芯片、启用的插件清单 |

## 4. "一切皆插件"：借鉴 DeepSeek Harness（Cordis）的映射与落地

### 4.1 DeepSeek Harness 是什么（参考基准）

- 2026-08 开源（MIT），构建在 **Cordis 元框架**上：内核**只做插件加载、卸载、依赖管理**，不承载任何业务能力。
- "Everything is a plugin"：模型适配器、工具目录、Skill、会话、沙箱、存储、**Agent 主循环**、调度、**UI**——九类核心能力全部是可装卸的插件；开发者通过配置替换任意层，不改内核源码。
- 插件即 npm 包，有插件管理页面（安装/停用/卸载/来源展示）。

**它对我们的启示不是"用 Cordis"，而是"先定内核边界"**：内核只负责注册/调度/配置，能力全外置——这正是嵌入式工具链（构建/烧录/调试/串口/OTA 天天在变、芯片天天在换）最需要的解耦方式。

### 4.2 概念映射表

| DeepSeek Harness（Cordis 插件） | 中控平台对应 | 落地方式 |
|---|---|---|
| 模型适配器 | **工具链适配器** | 每芯片/工具链一份配置（gcc 版本、openocd 脚本、链接脚本）；换 MCU = 换适配器 |
| 工具（Tool） | **能力插件** | build / flash / debug / serial / ota / crash——每个插件 = 动作 + 数据端点 + 面板定义 |
| Skill | **面板动作模板** | 如"一键升级"= 编译 → 双固件烧录 → 复位 → 验证心跳，串成编排脚本 |
| 会话（Session） | **设备会话** | 设备档案（COM/SWD/波特率）+ 连接状态 + 正在运行的动作 |
| 沙箱（Sandbox） | **构建/烧录原子性** | 构建目录隔离、烧录锁（防并发 openocd）、烧录前杀残留 |
| 存储（Storage） | **日志 / 固件库 / 配置** | `logs/` 现有落盘 + 固件产物归档 + `config.yaml` |
| Agent Loop | **遥测循环 / 升级状态机** | serial 心跳采集循环、OTA 5 状态机（从 iap_worker 复用） |
| 调度（Scheduling） | **动作队列与并发控制** | 现有 `running[]` 防重复触发扩展为队列 + 优先级 |
| UI | **前端面板插件** | 后端插件 manifest 声明"面板标题/动作按钮/数据端点"，前端动态渲染——**面板即插件** |

### 4.3 轻量插件契约（建议）

每个能力插件 = 一个目录，含 `manifest.json` + 一个 Python 包：

```json
{
  "id": "ota",
  "name": "OTA 升级",
  "version": "0.1.0",
  "depends": ["serial"],
  "actions": ["upgrade", "query", "reset_offset", "simulate_crc_error"],
  "endpoints": ["/api/ota/status", "/api/ota/progress"],
  "panel": { "title": "OTA 升级", "buttons": ["升级", "查询", "重置续传", "CRC 破坏模拟"] }
}
```

- 内核扫描 `plugins/` 目录，按 manifest 注册动作/端点/面板；
- `depends` 做依赖管理（如 ota 依赖 serial 的发送原语）；
- 前端启动时拉 `/api/plugins`，按 manifest 渲染面板——**新增能力 = 丢一个目录，不改内核不改前端框架**。

### 4.4 与 DSH 的刻意差异（为什么不做那么重）

| DSH 的做法 | 中控平台的做法 | 理由 |
|---|---|---|
| 插件是 npm 包，可热装热卸 | 插件是代码目录 + manifest，**重启加载** | 嵌入式场景插件少而稳定，热装卸的复杂度不值 |
| 内核是独立运行时（Cordis） | 内核就是 FastAPI 应用 + 插件管理器 | 不引入第二套运行时 |
| UI 也是插件（可换整套前端） | UI 是**面板级插件**（框架固定，面板可插） | 保持"简洁美丽"统一视觉，避免 UI 分裂 |
| 插件生态第三方开放 | 插件**私有为主**，设计上可扩展 | 工具链/协议是私有资产，先内聚 |

## 5. 渐进实施路线（三档，避免一步到位）

| 档 | 内容 | 交付 | 验收 |
|---|---|---|---|
| **档 1（近期，复用最大化）** | ① 后端从 pwsh 迁 Python（FastAPI），动作仍 subprocess 调 pwsh 脚本；② OTA 核心（protocol/firmware/iap_worker）搬入 `ota/` 服务模块；③ 前端新增 OTA 面板（HTML，复用现有风格） | 中控 v0.1：编译/烧录/调试/串口 + OTA 升级同界面 | OTA 面板完成真实固件升级（复用 AT32 Bootloader 协议）；驾驶舱功能零回退 |
| **档 2（中期，插件化）** | ① 插件管理器（manifest 扫描 + 注册表 + 依赖）；② 现有能力改造成插件（build/flash/debug/serial/ota/crash）；③ 配置中心（设备档案/插件清单） | 中控 v0.2：能力全插件化，`plugins/` 目录可增删 | 新增一个"模拟插件"（如 CAN 调试器）不改内核即可上线 |
| **档 3（远期，平台化）** | ① 多设备/多芯片档案；② 事件总线 + SSE 全链路（遥测/进度/动作状态）；③ 插件远程管理（类似 DSH 插件页） | 中控 v1.0：边缘管理中控平台 | 一台中控管 AT32/STM32 多板卡，切换芯片 = 换工具链适配器插件 |

## 6. 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| 1 | pwsh 脚本资产迁移 Python 后失联 | 档 1 用 subprocess 包装，脚本保持可独立运行；Python 只做调度/日志，双轨并行 |
| 2 | OTA 核心搬入后端后协议行为漂移 | 以 STM32-OTA-QT 原工程为回归基准：同一份 `protocol.py` / `firmware.py`，后端与 Qt 版共用测试向量 |
| 3 | 插件化过度设计 | 档 2 只做"注册表 + manifest"，不做热装卸/沙箱；等真实插件超过 5 个再评估加重 |
| 4 | 串口多插件竞争（ota 与 serial 都用串口） | 串口作为**唯一持有者插件**，其他插件通过它收发（`depends: ["serial"]`），避免双开 |
| 5 | Web 前端实时性不足 | 心跳/进度走 SSE；动作轮询兜底；前端"实时开关"已有先例（dashboard 实时:开/停） |
| 6 | 浏览器跨域 | 后端与前端同源（后端托管 HTML），保持现有 `http://127.0.0.1:8080/` 单端口模式 |

## 7. 决策记录

| 决策点 | 结论 | 依据 |
|---|---|---|
| 平台形态 | **Web（Python 后端 + 浏览器）** | 驾驶舱已 Web 化；OTA 核心纯 Python；边缘管理/远程/AI 接入天然 |
| 后端框架 | **FastAPI**（或 aiohttp） | SSE/WebSocket 原生；Python 生态与 OTA 核心无缝 |
| 前端 | **原生 JS 延续 dashboard.html** | 简洁美丽已有先例；面板即插件注册 |
| OTA 上位机 | **核心并入后端，PyQt6 壳丢弃** | 壳无价值，核心零改动可复用 |
| 插件化 | **轻量 Cordis 式：manifest + 注册表，三档渐进** | 同构 DSH 理念，但不引入重运行时 |
| 底层脚本 | **保留 pwsh 脚本，subprocess 调度** | 已全链路验证，迁移风险最小 |
